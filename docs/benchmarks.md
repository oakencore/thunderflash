# Benchmarks

Two different things get measured here. `scripts/bench.sh` measures the
software: how fast thunderflash can walk a tree, frame it, and write it back
down when the network is not the bottleneck. The two-Mac procedure at the
bottom measures the cable.

## Localhost harness

```sh
bash scripts/bench.sh
```

Environment:

| Variable | Default | Meaning |
| --- | --- | --- |
| `TF_BENCH_DIR` | `/tmp/tf-bench` | Fixtures, destination, and logs live here |
| `TF_LARGE_GIB` | `16` | Size of the single-file workload |
| `TF_SMALL_COUNT` | `10000` | Number of 4 KiB files |
| `TF_MEDIUM_COUNT` | `10000` | Number of 1 MiB files |
| `TF_QUEUE_DEPTH` | `4` | Chunk buffers in flight per side; clamped to 1..=64 |

The script builds `target/release/examples/bench`, generates fixtures once
(reused on later runs), then for each workload starts a receiver, reads the
`PORT` line it prints, runs a sender against it, and waits for both to exit.
Both sides run under `/usr/bin/time -l`, so the summary table carries CPU time
and peak RSS for each. Throughput is payload bytes divided by the sender's
`elapsed_s`, which times the `send_to` call only.

Per-run logs are left in `$TF_BENCH_DIR/logs/<workload>.{send,recv}.log`.

The `tf` CLI cannot be used for this: it binds `bridge0` and refuses to fall
back to another interface, so the harness is a cargo example that calls the
library over 127.0.0.1 with a fixed token.

### Workloads

| Workload | What it isolates |
| --- | --- |
| `large-cold` | Steady-state streaming of one big file: chunk loop, socket, disk |
| `large-warm` | The same transfer immediately again — the delta is cache effects |
| `small-4KiB` | Per-file overhead. Bytes are irrelevant; entry framing, `openat`, and `mkdir` dominate |
| `medium-1MiB` | The crossover point where per-file cost and per-byte cost are comparable |
| `mixed` | A realistic tree: a few 100 MiB files, hundreds of small ones, empty files, empty dirs, symlinks |
| `edge` | Correctness under timing: a file of exactly `CHUNK` (4 MiB), one byte under, one byte over, plus empties |

`walk_s` in the table comes from the sender's own `Diag::walk_nanos`, i.e. the
walk inside the timed send, so the cost of enumerating the tree can be read
apart from the cost of transferring it without walking the tree twice.

## Two Macs over Thunderbolt

The only measurement that says anything about the cable. Connect both Macs,
confirm **Thunderbolt Bridge** is up in System Settings > Network on both.

On the receiving Mac:

```sh
mkdir -p /tmp/tf-dest && tf recv /tmp/tf-dest
```

It prints an address and a three-word phrase. On the sending Mac, using a
fixture generated by the harness:

```sh
cargo build --release --example bench
./target/release/examples/bench fix large=16 /tmp/tf-fix/large
tf send /tmp/tf-fix/large
```

`tf` prints live and final throughput on both ends. Delete `/tmp/tf-dest`
between runs, or the receiver is overwriting files rather than creating them.

### MTU

Default is 1500. Measure that first, then raise it on **both** Macs. macOS
rejects `mtu 9000` on `bridge0` while its members are at 1500, so set the
members first:

```sh
ifconfig bridge0 | grep member       # e.g. en1 en2 en6
sudo ifconfig en1 mtu 9000           # repeat for each member
sudo ifconfig bridge0 mtu 9000
```

Confirm jumbo frames actually pass before re-running
(`ping -D -s 8000 <peer>`), re-run the same transfer, then revert (same
commands with 1500, members last). Neither setting persists across a reboot,
and `tf` never changes it itself — it only prints a hint when it sees 1500.

### Measured: M5 MacBook Pro to M4 MacBook Pro (2026-08-18)

A mixed pair — the M5 side is Thunderbolt 5, the M4 side Thunderbolt 4 — so
the link negotiated **40 Gb/s** (TB4 mode; confirmed with
`system_profiler SPThunderboltDataType`, which reports the unused TB5 ports
as "Up to 120 Gb/s" and the connected one as "40 Gb/s"). A TB5-to-TB5 pair
remains unmeasured. 29.7 GB of real media files (39 files, 5 dirs), sender
the M5 Max. Single runs; `--stats` on both ends.

| mode | MTU | elapsed | throughput | sender CPU (user+sys) |
| --- | --- | --- | --- | --- |
| verified (default) | 1500 | 13.0 s | 2.28 GB/s | 12.09 + 2.72 s |
| `--no-verify` | 1500 | 7.9 s | 3.73 GB/s | 0.01 + 2.70 s |
| `--no-verify` | 9000 | 8.1 s | 3.64 GB/s | 0.01 + 2.61 s |

Verified throughput sits on the single-core BLAKE3 ceiling (~2.4 GB/s — the
sender spent 12.19 s of the 13.0 s hashing, with 6,987 pool stalls showing
backpressure holding the reader). `--no-verify` runs at the disk/link limit
with essentially zero sender user CPU and zero pool stalls. Jumbo frames
changed nothing measurable on this pair: the ~3.7 GB/s ceiling is not
per-packet overhead. Peak sender RSS was 28 MB in every run.

## What these numbers are not

**Localhost is not Thunderbolt.** The loopback path has no cable, no PHY, and
no MTU. A localhost number is an upper bound on what the software can do; the
cable number is always lower. Do not quote a localhost GB/s figure as a
transfer speed.

**Both endpoints share one machine.** Sender and receiver compete for the same
cores, the same page cache, and the same SSD, and the reader thread's disk
reads race the receiver's writes to the same device. On a real pair of Macs
each side has a whole machine. Expect the localhost numbers to understate CPU
headroom and overstate contention.

**"Cold" is best-effort.** A file large enough to defeat the page cache would
need to exceed RAM (>128 GiB on this machine), which is impractical to
generate and transfer per run. `large-cold` only means "first run against a
freshly created destination"; `large-warm` is the immediate rerun, and the gap
between them is the honest statement of how much caching is in play. Both ends
set `F_NOCACHE` on the file descriptors they open, so page-cache warmth mostly
affects fixture generation rather than steady-state transfer — which is why
the two runs are usually closer than the labels suggest.

**Fixture contents are incompressible.** Files are filled by a xorshift64\*
PRNG rather than `/dev/zero`, so nothing in the stack can win by
special-casing runs of zeroes.

## Optional manual measurements

Neither of these is automated: one needs `sudo` and the other needs a
different build.

**Per-phase timings** come from `--stats` on either `bench` subcommand, which
prints the same block as `tf send --stats` / `tf recv --stats`. `metadata` on
the receiver is the per-entry path (sanitize, `walk_dirs`, `create_file_at`);
watch it against `total` when a small-file workload regresses. On the receiver
`total` excludes the wait in `accept`, which is reported separately as
`waiting`.

**Syscall counts** need dtrace, which needs root (and SIP disabled for some
probes):

```sh
sudo dtrace -n 'syscall:::entry /pid == $target/ { @[probefunc] = count(); }' -c './target/release/examples/bench send 5000 /tmp/tf-bench/fixtures/small'
```

**Durability and no-verify comparisons** are not in `bench.sh`; run the harness
by hand, receiver first, then the sender against the port it prints:

```sh
./target/release/examples/bench recv --durable /tmp/tf-bench/dest
./target/release/examples/bench send --no-verify <port> /tmp/tf-bench/fixtures/large
```

**Allocation counts** need an instrumented global allocator — a counting
wrapper around `System` compiled into the example — which is a source change,
so it is deliberately not part of the harness. Peak RSS from `/usr/bin/time -l`
is in the summary table and is usually enough to notice a regression: the
sender is bounded by `(QUEUE_DEPTH + 2) * CHUNK` (24 MiB at defaults — one
buffer per queue slot, plus one being filled and one being written), the
receiver by `QUEUE_DEPTH * CHUNK` (16 MiB). Both scale with `TF_QUEUE_DEPTH`,
and both sit on top of the 8 MiB socket buffers each side sets.

## sendfile spike

Asked once and answered: would `sendfile(2)` on the sender be worth a second
transfer engine? Measured with a throwaway two-process harness (since deleted)
over 127.0.0.1, same 8 MiB `SO_SNDBUF`/`SO_RCVBUF` and `TCP_NODELAY` as
`send_to`, sending `fixtures/large/large.bin` (16 GiB) while the receiver only
drained and counted. Five sender variants, three runs each, mean reported.
`rw-pipe-nocache` is the like-for-like baseline: reader thread plus pooled
4 MiB buffers feeding the socket writer, i.e. exactly what `send.rs` does with
`--no-verify`. `sendfile` variants issued 128 MiB slices, so per-slice progress
reporting would still be possible.

| Sender variant | GB/s | Sender CPU (s / 16 GiB) | Receiver CPU (s / 16 GiB) |
| --- | --- | --- | --- |
| `rw` (single-thread read+write) | 9.01 | 1.93 | 0.99 |
| `rw` + `F_NOCACHE` | 9.62 | 1.79 | 0.95 |
| `rw-pipe` + `F_NOCACHE` (**baseline**) | 13.67 | 2.14 | 1.07 |
| `sendfile` | 16.18 | 1.06 | 0.80 |
| `sendfile` + `F_NOCACHE` | 16.04 | 1.07 | 0.80 |

**Rejected.** Against the real baseline `sendfile` is +17% throughput, short of
the >25% bar, and both numbers are 3-5x above anything a Thunderbolt bridge
delivers — on the cable the sender is not the bottleneck, so the win is
invisible. The halved sender CPU (1.07s vs 2.14s per 16 GiB) is real but it is
one core of sixteen, idle either way. Worse, `sendfile` never puts the bytes in
userspace, so BLAKE3 verification would need a second read of the whole file
(out of budget), meaning the win only ever applies to `--no-verify` — the
non-default path — while the cost is a parallel payload engine that duplicates
buffer pooling, shrink detection, progress and diag accounting. `F_NOCACHE`
makes no difference under `sendfile` and only a small one to the read loop here,
because a 16 GiB fixture fits in 128 GiB of RAM; treat these as upper bounds.
